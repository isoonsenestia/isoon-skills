# i18n — next-intl

All repos use `next-intl` **except NESTA_UI**.

## Pages Router

`getStaticProps` + `useTranslations()`:

```tsx
// pages/appointments.tsx
export async function getStaticProps({ locale }: { locale: string }) {
  return {
    props: {
      messages: (await import(`../../locales/${locale}.json`)).default,
    },
  }
}

const AppointmentsPage: NextPageWithLayout = () => {
  const t = useTranslations()
  return <h1>{t('appointments_page.title')}</h1>
}

AppointmentsPage.getLayout = (page) => <Layout>{page}</Layout>
export default AppointmentsPage
```

## App Router

Layout provides `NextIntlClientProvider`; components call `useTranslations()`. Messages load once in `app/[locale]/layout.tsx` (or root layout). No `getStaticProps`.

```tsx
"use client"
import { useTranslations } from "next-intl"

export default function AppointmentCard() {
  const t = useTranslations("appointment_card")
  return <span>{t("title")}</span>
}
```

## App Router navigation + gotchas

- **Locale-aware navigation:** import `useRouter`, `Link`, `redirect`, `usePathname` from the repo's `@/i18n/routing` (next-intl `createNavigation`) — **not** from `next/navigation`. `router.push("/foo")` then auto-prefixes the active locale; using `next/navigation` drops it and breaks locale routing.
- **`useSearchParams` in a client component needs a `<Suspense>` boundary** — wrap the client container in `page.tsx` (`<Suspense fallback={null}>`), or the build warns and the route is forced fully dynamic.
- Some LIFF repos ship **`th.json` only** (no `en.json`). Add keys to whatever locale files actually exist; don't assume `en.json`.

## Rule

Every user-visible string goes through `t()`. Never hardcode Thai or English strings in JSX. Add new keys to `locales/th.json` and `locales/en.json` (if present in this repo). Use **literal** keys in `t()` (e.g. `t("errors.INVALID_AGE")`), not dynamic template strings, so typed-message setups don't break.
